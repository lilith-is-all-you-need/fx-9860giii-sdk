## A. 源码、网络、版本和工具链

### 01. 浏览器取不到源码，不等于源码不可获得

- **状态：历史误判已纠正。**
- **现象：** 早期访问 `giac35/src0` 的结论偏向“拿不到源码”；旧域名 curl 出现证书主机名不匹配，网页服务也无法打开部分页面。
- **当时误判／试验假设：** 把一种客户端或一个旧域名的失败，上升为源码整体不可取得，并可能因此提前转向重写内核。
- **定位证据：** 正常 TLS 校验下，新域名 Range 返回 206，完整下载返回 200、24,743,111 B；backup 下载 SHA-256 一致。Windows 走既有本地代理，WSL 独立请求也取得 206。
- **修复／实验结果：** 恢复五份固定哈希归档，主包 4,687 个条目，39 个 CAS 对象均找到对应源文件；没有关闭证书校验，也没有执行下载的脚本或二进制。
- **剩余边界：** 这是当时可达性与完整性证据，不保证今后可达，也不等于集成/构建完成。
- **跨项目预防法：** 分开记录 DNS/TLS/HTTP/下载校验；对官方更名域名、官方备份、不同本地客户端交叉探测；在宣布“依赖不可得”前保留原响应。
- **原始依据：** SOURCE_RECOVERY（原工程：`khicas-addin/SOURCE_RECOVERY.md`）、固定下载清单（原工程：`khicas-addin/dependencies/giac35/manifest.json`）。

### 02. 代理 CONNECT、HTTP 000、超时与目标站 403 是不同结果

- **状态：历史误判已纠正；Fygue 源码仍未取得。**
- **现象：** Fygue PR/API/归档/Git refs 在限时探测中超时；若干 header 只有代理的 `200 Connection established`。先前 ROM 映射审查记录过网页工具的 403。
- **当时误判／试验假设：** 把 curl 的 HTTP 000 当作目标站拒绝，或把代理隧道建立当作目标代码下载成功；再把未取得源码等同于不存在/私有。
- **定位证据：** 限时核查逐端点保存 12 秒超时、状态 000、无响应体；GitHub API 的未认证限额 403 与作者公开仓库 HTML 200 是另外两件事。
- **修复／实验结果：** 最终结论限定为“本环境未取得源码，commit/hash 未知”；没有用 GintTrace、vxGOS 充当 Fygue 同一实现。
- **剩余边界：** 没有源码就无法验证块枚举、页租约或 GIII OS03.70.0200 适配。
- **跨项目预防法：** 网络报告保留客户端、实际 URL、代理层、目标 HTTP 状态、字节数和响应哈希；将超时、权限、404 与未发现分栏。
- **原始依据：** 公开入口核查（原工程：`khicas-addin/audit/fygue-source-access-20261114/README.md`）、请求记录（原工程：`khicas-addin/audit/fygue-source-access-20261114/curl-access-results.json`）。

### 03. 对象对应源文件齐全，不等于原版可从源码完整重建

- **状态：部分验证／原版复现未完成。**
- **现象：** 原 `src0/Makefile` 的 39 个 CAS、6 个 UI、4 个启动/系统调用/语言菜单对象均有源文件，启动汇编和链接脚本也在包内。
- **当时误判／试验假设：** “直接对象源没缺”容易被写成“所有依赖源码齐全，已经能复现原版”。
- **定位证据：** `libc/Makefile` 先复制预编译 `libfx.a`，然后加本地对象；对应完整源码/recipe 未识别。`libm.a` 也预编译，五个固定归档中没有找到所搜索的匹配数学实现。库注释分别出现 GCC 4.6.3、7.3.0。
- **修复／实验结果：** 清单区分“直接源完整”和“可复现构建未完成”，没有以库中 GCC 字符串断定核心编译器。
- **剩余边界：** 原 compiler/binutils/library 组合及 clean 原 UI+runtime+CAS 构建仍未知。
- **跨项目预防法：** 按最终链接闭包列每个归档、成员来源和构建命令；预编译依赖单独标识，不能只统计项目 `.cc` 数量。
- **原始依据：** 恢复更正（原工程：`khicas-addin/SOURCE_RECOVERY.md`）、原始清单（原工程：`khicas-addin/audit/original-source-inventory-20261115/inventory.json`）、依赖检索（原工程：`khicas-addin/audit/original-source-inventory-20261115/dependency-search.json`）。

### 04. 同一个下载目录里的源、ELF、转储、日志和 G1A 不一定同源同批次

- **状态：历史误判已纠正；精确对应未证实。**
- **现象：** 主归档内英语 G1A 是 2,094,380 B、头日期 2022.1113.1801；保留原版是 2,094,444 B、头日期 2023.0705.1233，相差 64 B。
- **当时误判／试验假设：** 因为源包附带可运行文件和符号转储，就把它们当作该包一次 clean 成功构建的证明。
- **定位证据：** 官方目录把源码列为 2022-11-14、英语二进制列为 2023-07-05；包内 `src0/log` 实际记录 `console.cc` 的 `handle_f5`、`lang`、`inputline` 编译失败。
- **修复／实验结果：** 保留源、二进制、日志的各自哈希和日期，不再声称已经证实源到二进制关系。日期不同也没有被反向写成“已证明少了某个补丁”。
- **剩余边界：** 旧失败日志不能证明当前归档重新编译一定失败；附带 G1A 也不能证明归档现在能成功重建。
- **跨项目预防法：** 为每个产物绑定完整输入清单、链接命令和成功日志；归档里“挨在一起”不建立来源关系。
- **原始依据：** SOURCE_RECOVERY（原工程：`khicas-addin/SOURCE_RECOVERY.md`）、目录与二进制核对（原工程：`khicas-addin/audit/original-source-inventory-20261115/inventory.json`）。

### 05. v21、Giac 2.1、fxSDK 版本字段与源码版本混淆

- **状态：历史误判已纠正。**
- **现象：** 文档里同时出现 v17/v18/v21、Giac 2.1.0、历史 `VERSION "1.4.9-57"`，原 G1A 头还有 `fxSDK.1337`。
- **当时误判／试验假设：** 把项目验证批次 v21 读成 Giac 2.1；把包装 metadata 或某个残留版本宏当作整个代码树年龄。
- **定位证据：** 恢复源的 config 明确 1.4.9-57；官方新版独立归档由 `configure.ac` 标为 2.1.0；GeoGebra 镜像曾有较新 commit 却残留 1.2.3 宏。uSTL 也有同类冲突：目录叫 `ustl-2.1`，保存的 config 却自报 `USTL_STRING "ustl v1.6"`、`USTL_VERSION 0x160`。
- **修复／实验结果：** 目前历史核心记为“1.4.9-57 派生、39 单元、v21 验证批次”；新版 48 单元试验另列。
- **剩余边界：** 旧移植树可能有后续回补，不能把其中每个算法都归结为纯 1.4.9 原始实现。uSTL 的目录名与生成头均不足以单独确定整包纯净上游版本，其精确谱系仍需核实。
- **跨项目预防法：** 同时保存上游身份、项目修订、工具链版本、包版本、产物哈希；产品名称不替代源码身份。
- **原始依据：** 身份更正（原工程：`khicas-addin/SOURCE_RECOVERY.md`）、旧版本审计（原工程：`khicas-addin/audit/giac-2.1.0/v18-audit.md`）、v21 定义（原工程：`khicas-addin/audit/v21-20261114/README.md`）、uSTL 自报配置（原工程：`khicas-addin/audit/giac-2.1.0/evidence/legacy/ustl-2.1/config.h`）。

### 06. 同名安装文件掩盖了 Compact 与真实 Giac 的实现差别

- **状态：已明确隔离；仍需持续标识。**
- **现象：** 根目录和多个 release 都有 `KhiCAS-Next.g1a`；根目录文件对应 CAS02、106,568 B，使用独立精简 C 内核。
- **当时误判／试验假设：** 把能生成的小安装包当成体积超限的完整历史 Giac 或 Giac 2.1 已经发布。
- **定位证据：** README 明确 CAS02 的四个应用单元是 `main.c/ui.c/compact_cas.c/compact_cas_port.c`，不链接完整 Giac；功能有六次多项式、4×4 矩阵等边界。
- **修复／实验结果：** UI About 和 release 文档标注 Compact CAS；真实内核试验保留独立审核目录，超限不打包。
- **剩余边界：** CAS02 自己的主机/处理器验证同样不构成真机验收；其命令范围也不能用于证明 full CAS 等价。
- **跨项目预防法：** 将实现身份和构建 profile 嵌入 About、manifest、release 名称；最终交付摘要必须指出用户手中实际是哪条实现。
- **原始依据：** README 的 CAS02 说明（原工程：`khicas-addin/README.md`）、CAS02 使用范围（原工程：`khicas-addin/releases/CAS02/USAGE.md`）。

### 07. 工具链存在，却被可执行文件命名检查判成缺失

- **状态：历史误判已纠正。**
- **现象：** 初版检查只找 `sh3eb-elf-gcc/g++/ld/objcopy`；现代 fxSDK 调用的是 `sh-elf-*`，sysroot/target triplet 仍可叫 `sh3eb-elf`。
- **当时误判／试验假设：** 缺少旧名字就断言编译器没装好，甚至归因于 SH3 与 GIII SH4A 不兼容。
- **定位证据：** 本地 fxSDK CMake 选择 `sh-elf-gcc`，配置/sysroot 仍出现 `sh3eb-elf`；诊断同时承认早期确实缺过完整依赖链。
- **修复／实验结果：** 检查器接受两类命名，区分“检查器假阴性”和“当时确实缺库”。没有因修正检查器就抹掉真实安装缺口。
- **剩余边界：** 指令集向上兼容不能证明 syscall ABI、缓存、内存映射或 G1A loader 相同。
- **跨项目预防法：** 检查编译器报告的 target、multilib 和实际最小链接能力，避免将某个历史命令名作为唯一检测条件。
- **原始依据：** 前置工具链诊断（原工程：`../../../khicas-dev/toolchain_diagnosis.md`）。

### 08. 第一遍 GCC 没有 libstdc++，并不必然是失败安装

- **状态：历史误判已纠正。**
- **现象：** fxSDK 依赖安装是两遍：先 binutils/GCC，再 OpenLibm/fxlibc，再回头构建目标 C++ 库；早期 Windows/MSYS2 环境也缺 POSIX/链接/路径条件。
- **当时误判／试验假设：** 把阶段性不提供 C++ 库视为编译器损坏，或把宿主 Windows 的脚本失败解释为 SuperH 后端不支持。
- **定位证据：** 前置诊断明确列出安装顺序、实际缺失 sysroot 和旧 Hitachi SDK 不能代替 GCC 栈；WSL 内 `fxlink` USB 限制也是传输问题，不是编译问题。
- **修复／实验结果：** 历史环境按 Linux/WSL 工具链链条恢复；后续 WSL 故障另由独立 Linux VM 承担审计。
- **剩余边界：** 当前所有旧安装说明都有时间范围，不能当成今日机器仍处于同一状态。
- **跨项目预防法：** 把安装拆成可独立验收的 compiler、C sysroot、C++ runtime、SDK、packager 五层；每层用自己的小样例验证。
- **原始依据：** 工具链诊断及安装顺序（原工程：`../../../khicas-dev/toolchain_diagnosis.md`）、独立环境恢复（原工程：`khicas-addin/audit/build-env-20261114/README.md`）。

### 09. 构建环境卡死，不应通过重置用户全部环境来掩盖

- **状态：已建立隔离恢复；旧环境故障未被宣称修好。**
- **现象：** 用户 WSL2 不能启动，任务 WSL1 也失去响应，连列举/终止请求超时；直接引用转移试验因此没有取得编译或性能结果。
- **当时误判／试验假设：** 容易把被环境中断的试验写成候选失败，或把重启全局 WSL/改用户配置当成必要前提。
- **定位证据：** build-env 保存独立 Ubuntu/QEMU 环境和输入来源，用户 `.wslconfig` 与备份哈希一致；gen-copy 文档明确 direct 候选无结果。
- **修复／实验结果：** 审计在任务专用 VM 恢复，工具包保留 Unix 权限/链接；没有重启 Windows、全局 shutdown WSL 或改用户发行版。
- **剩余边界：** 这只是替代构建环境，不证明原 WSL 修复；旧 WSL1 专用 mmap shim 也不能带入正常 Linux 或设备程序。
- **跨项目预防法：** 环境故障、候选编译失败、候选功能失败分别编号；恢复输入后核对清单，不从中断输出补造最终状态。
- **原始依据：** 构建环境（原工程：`khicas-addin/audit/build-env-20261114/README.md`）、被中断的 direct 试验（原工程：`khicas-addin/audit/gen-copy-assign-20261114/README.md`）。

## B. 体积测量、容量与失败的缩容方向

### 10. 剩余存储、MB/MiB、项目预算和 OS 识别边界被混在一起

- **状态：历史误判已纠正；精确 OS 门限未知。**
- **现象：** BASE01 曾针对约 8 KiB 剩余存储缺口生成 BASE02；BASE02 可复制但不被识别。小诊断后来证明 2,000,000 B 可开，2,859,592 B 不识别。
- **当时误判／试验假设：** 认为总存储够就能运行单个 add-in；把保守 2,000,000 B 预算写成设备硬上限，或把“1.99 MB”显示当原始字节数。
- **定位证据：** 用户随后确认原版 2,094,444 B 可打开；2 MiB 是 2,097,152 B，原版距它还有 2,708 B。

- **剩余边界：** 没测出精确识别边界；原版退出和完整数学回归也不在该大小反馈中。
- **跨项目预防法：** 原始 B 作为主数据，显示单位仅辅助；容量表分别列总存储、单文件识别、映射跨度和保守发布预算。
- **原始依据：** 安装诊断（原工程：`khicas-addin/audit/hardware-20261114/installation-recognition.json`）、最新大小反馈（原工程：`khicas-addin/audit/hardware-20261115/original-khicas-size.json`）。

### 11. 链接器的计量空间与设备可部署空间不是一回事

- **状态：历史误判已纠正；超限候选继续拒绝。**
- **现象：** 原 SDK 500 KiB ROM/6 KiB RAM 布局无法链接真实内核；后来的测量使用较大布局。BFD 对 `.eh_frame` 去重的中间布局又曾使 3,071 KiB 链接误报溢出。
- **当时误判／试验假设：** 扩大链接脚本后成功便称可部署；相反，也可能把链接中间布局的溢出当成最终文件一定同样大。
- **定位证据：** foundation 区分测量链接工作空间、最终 LOAD 段、实际 objcopy 长度及完整 G1A 长度；常规门禁另行执行。
- **修复／实验结果：** 大布局只用于计量，发布判断依据最终产物与明确预算；v21 和最新候选都没有因测量能链接就发布 G1A。
- **剩余边界：** 最终静态尺寸合格仍需 OS 识别和实际运行，不能倒推硬件映射容量。
- **跨项目预防法：** measurement profile 明确命名；允许计量与允许打包使用不同命令及门禁，报告必须写出最终 gate 结果。
- **原始依据：** 基础容量记录（原工程：`khicas-addin/audit/foundation/README.md`）、早期目标链接失败（原工程：`khicas-addin/audit/giac-2.1.0/v18-audit.md`）、v21 容量拒绝（原工程：`khicas-addin/audit/v21-20261114/README.md`）。

### 12. 只数 text/rodata，漏掉完整 ROM 映像末尾 1,020 B

- **状态：已修复。**
- **现象：** 旧 ROM mapping 比实际最后 ROM load 字节短 1,020 B；`.eh_frame`、`.data` ROM 初值和 `.gint.mapped` 有内容落在边界之外。
- **当时误判／试验假设：** 把主代码段结束当完整可加载内容结束；初始化数据在 RAM 中运行，就忘记它的 ROM 初值仍占文件/映射。
- **定位证据：** 负例 mapping end 6,219,944、payload end 6,220,964，多个 file-backed LOAD 未覆盖；BSS 则明确不应加入 ROM 文件字节。
- **修复／实验结果：** 加入逐 LOAD/allocated section/最终二进制交叉核验，保存修复前负例及修复后报告。
- **剩余边界：** 映像覆盖正确不等于 OS 已接受这么大的映像。
- **跨项目预防法：** 用 LMA/文件载荷而非 VMA 或单节汇总判定 ROM；检查最后一个有文件内容的字节，并独立核对 objcopy 长度。
- **原始依据：** 映射负例（原工程：`khicas-addin/audit/foundation/rom-mapping-negative.json`）、映射修复后（原工程：`khicas-addin/audit/foundation/rom-mapping-positive.json`）。

### 13. 链接图把共享字符串算到 main.o，夸大了 UI 成本

### 15. 删除注册名字，并不等于移除算法及其共享依赖

### 19. 共享排序与清理帧的对象级收益，不是整核净收益

### 20. 8字节 gen 能省 RAM，不一定能省 ROM，且标签迁移范围远大于一个 struct

- **状态：失败的 ROM 缩容假设／保留12 B布局。**

- **当时误判／试验假设：** 每对象省4 B，因此整包会按同样比例缩小；把历史8 B表示直接恢复就能同时保留当前全精度和安全语义。

- **跨项目预防法：** 先抽象访问/所有权接口，再改编码；用全核最终链接验证ROM，不按对象尺寸乘估全部缺口。
- **原始依据：** gen8 完整实验（原工程：`khicas-addin/audit/gen8-20261114/README.md`）。

### 23. 应用打开异常，不会补上标准库被-fno-exceptions删掉的展开信息

- **状态：已在隔离运行库修复；完整设备仍未验证。**
