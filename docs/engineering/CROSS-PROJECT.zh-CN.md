# 可迁移到其他项目的工程方法

本章把 KhiCAS 开发中的实际问题归纳成通用方法。适用于资源受限设备、旧代码移植、跨平台构建、性能优化、插件加载和长期代理协作。每项方法说明适用条件与检查动作；它们不是对其他项目已经发生故障的断言。具体案例与原始证据见[失败案例](KHICAS-CASEBOOK.zh-CN.md)。

## 先建立能比较的基线

### 工作产品与源码基线分开确认

用户手里有一个能运行的产品，只证明该二进制在那个环境可用。它不自动证明网上的同名源码、最新分支、旧 SDK 能重建该产品。接手旧项目时先保存工作产物，记录字节数、哈希、版本字段、设备/OS 和关键操作；再单独记录源码归档、依赖与构建工具。

本次源码包自带程序与用户原版只差 64 B，仍不足以建立精确复现关系。其他项目中的 APK、固件、模型权重、数据库导出也有相同问题。发布物的日期不能替代源码提交；文件修改时间不能替代构建日期。

### 先复现再迁移

先用原配置建立一个功能、体积、内存和速度的基线，再替换运行库、编译器、UI 或算法。一轮同时替换多个底层部件，会让后续回归无法定位到一个因素。若原环境无法复现，将它明确列为独立工作，不把现代化改造后的体积当成原版大小的自然结果。

一个实用的比较顺序是：固定数学/业务源码，只换构建环境；固定环境，只换接口；固定接口，只加入修复。并非每个项目都能做到完全单变量，但必须记录哪些变量一起变化，不能伪装成同条件实验。

### 开工前定义交付状态

区分源码存在、编译成功、链接成功、可打包、可安装、可启动、核心功能通过、系统生命周期通过和长期运行稳定。这些状态不互相替代。为每个交付状态列一个可观察的验收动作，避免把若干漂亮测试数字误当最终用户可用。

## 把资源预算作为设计输入

### 容量不是一个数字

先区分总存储、单文件限制、加载地址范围、映像实际长度、运行时堆、静态区和栈。数据库项目也要区分文件大小、索引大小、缓存和事务日志；桌面项目要区分安装包、解压后体积、常驻内存与峰值。

预算表至少应包含：数值及单位、来源、测量对象、时间、是否实测硬限制、预留余量。把保守策略写成策略，不写成设备事实。边界只有上下样本时写区间，不以中间的整齐数字补全结论。

### 测净差而非模块名义大小

静态库、对象文件和源文件行数不能表示删除它之后的净收益。内联、公共函数、注册表、模板、对齐和链接根集合都会改变结果。用同一完整产品配置重链接 A/B，比较最终加载映像；同时记录外部文件、加载器、导入表、缓冲和恢复成本。

看到一个 18 KiB 模块时，要分别问：源库少了多少、主程序最终少了多少、模块加载占多少 RAM、总安装文件增加多少，以及运行速度如何变化。任何一个数字都不应替代另外四个。

### 预算余量有明确用途

余量用于分配器元数据、对齐、错误处理、缓存、驱动和未来修复。不要把当前空余全部分给一个组件，然后假定系统服务免费。若更改预算，重新检查实际编译对象和运行池，而不只改文档或文件名。

### 设定方案继续与停止的条件

实验开始前写出要验证的假设、预期产物、比较基线、成功门槛和停止条件。一次小模块实验成功，只回答小模块机制问题；若净收益远小于剩余缺口，不应自动扩大为完整架构工程。成本和收益都应由测量决定。

## 源码与下载的可靠性

### 分层诊断网络

区分 DNS、TCP、TLS、代理握手、HTTP 状态、内容长度和文件校验。`200 Connection established` 只表示代理隧道，curl 状态 `000` 表示未拿到 HTTP 响应；都不能写成上游下载成功或服务器拒绝。浏览器检索工具不可读也不证明本地普通下载不通。

Windows、WSL2、WSL1、VM 的网络和代理环境可能不同。特别是本机回环代理与 NAT 地址不是同一可达范围。记录发起请求的环境和超时界限，保留原始头与错误；不要为“修下载”默默关闭证书验证。

### 依赖身份要固定

保存 URL、观察日期、长度、SHA-256、上游版本/提交、许可证文件位置。哈希证明后来拿到的是同一份内容，不等于证明作者身份。签名、厂家公布哈希和自算哈希分别说明用途，不能混成“官方认证”。

归档目录名、配置宏、预编译库的编译器字符串可能不一致。记录冲突，避免给不确定版本强行命名。同名 `libc.a` 在不同 sysroot 下可能完全不同；“链接了 libc”不足以说明依赖身份。

### 脚本不能默认都是只读

先看脚本入口和副作用，再把它放入检查手册。一个名字叫 inspect 的脚本可能自动写证据或下载，`--help` 也可能被顶层代码之前的初始化影响。对来源不清楚的构建脚本先审查，再在隔离环境运行。不要把文档中的命令当成已执行事实。

## 跨平台文件和命令

### 路径就是数据

空格、撇号、中文和长路径应作为正常输入支持。尽可能以参数数组传进程，避免生成多层 shell 字符串。JSON 转义不是 PowerShell、Bash 或 cmd 的转义；把 JSON 文本插入 shell 不会自动防止命令替换。

Windows 文件操作使用 `-LiteralPath` 等字面路径方式。递归移动或删除前解析绝对路径并检查目标边界。不要在一个 shell 枚举文件，再用另一个 shell 拼接删除命令。手册中的清理示例应限定可再生成的专用输出目录。

### 行尾、编码和大小写分别处理

CRLF 可能把 shebang 中的解释器变成 `bash\r`；Latin-1 注释被当 UTF-8 重写会产生无关差异；`TeX.h` 与 `tex.h` 在默认 Windows 文件系统上可能合并。这三个问题不能用一次“统一格式”模糊处理。

需要保留 Unix 语义的源码在支持大小写区分的环境解包，或直接按归档成员校验。保留符号链接和执行权限。文本转换必须说明范围与编码，并对预期修改做精确补丁。检查预处理结果相同可帮助隔离注释变化，但不能替代最终产物身份检查。

### 不照抄破坏性环境修复

历史文档里的 `git reset --hard` 可能仅适用于可重新克隆的第三方临时目录，不能照搬到用户工作区。运行修复前先确定仓库身份、未保存内容和恢复来源。本项目当前没有 Git 历史可依赖，所以“回滚一下”必须有具体文件快照。

## ABI 和内存对象

### 跨库兼容包含对象布局

不仅要看函数名是否能链接，还要看大小端、指针宽度、对齐、调用约定、浮点表示、结构体字段、容器布局和异常模型。标准字符串与定制字符串即使名字相似也可能不能跨 ABI 传递。

对 ROM 常量别名、C/C++ 接口和手写汇编布局加入尺寸、对齐、偏移断言。使用填毒内存构造对象，检测未初始化字段；用真实目标编译器确认，不能仅用主机布局替代。

### 分配器的账必须闭合

记录请求长度与实际计费长度，包含头部、对齐和零长度语义。检查乘法与加法溢出，再分配，再建立所有权。失败时保留旧缓冲，成功时才交换。`realloc` 失败后不应丢失原指针。

跟踪堆预算不代表整个进程占用。异常应急池、C 库原生分配、符号缓存、栈和驱动可能不经过同一计数器。报告必须写清哪些入口已接入、哪些仍需审查。

### 生命周期与错误恢复一起设计

正常返回释放正确，并不说明第 N 次分配失败、构造一半、比较函数抛错或输出截断时正确。验证自赋值、源目标别名、共享引用、只读常量、部分构造和析构顺序。

不要把容器能按字节移动的内部假设推广到任意非平凡对象；不要把一个 `new` 包装成抛异常就认为旧容器获得了完整异常安全。错误清理必须与实际对象模型匹配。

### 回滚范围包含看不见的状态

候选上下文复制通常只能隔离一部分状态。解析时全局符号缓存、共享列表原地修改、全局排序回调、打印模式和程序状态，都可能越过上下文边界。先列可变状态清单，逐项决定复制、日志、撤销或保留策略。

事务提交应晚于完整输出检查。否则“结果太长”也可能已经修改变量。失败后应检查旧变量、Ans、后续简单表达式和实际内存用量，不能仅检查返回错误码。

### 用重复与新输入区分缓存和泄漏

同一名字重复一千次没有增长，不证明一千个不同名字不会增长。首次增加后稳定可能是缓存；不断新增键增长可能是设计保留，也可能导致可用容量耗尽。应分别测同名、新名、成功、失败、取消和重置。

结束时释放整个 arena 只能证明父池归还，不能证明其中每个对象正常析构。若运行中已无法继续计算，最后统一释放也不能弥补会话稳定性问题。

## 异常和系统恢复

### 业务错误、C++ 异常和硬件异常分开

它们有不同机制。关闭 C++ 异常并不表示不能报告错误；打开 `-fexceptions` 也不会自动使无异常构建的标准库、启动代码和链接脚本兼容。需要检查抛出者、所有传播栈帧、清理代码、元数据、注册和注销。

在资源耗尽时触发的错误路径本身也可能需要分配。测试第一次 OOM、应急池不可用、嵌套异常和启动失败，防止只在运行库已经预热时通过。

### 不用非局部跳转掩盖所有权

跨越有待析构 C++ 对象的粗暴跳转可能跳过清理。若系统选择无异常错误传播，应明确每层错误码、清理和状态恢复，而不是将异常统一替换成跳转。是否使用异常是一项架构选择，稳定性取决于所有失败路径是否闭合。

### 暂停、退出和重入是不同状态

应用返回菜单后可能被 OS 恢复，也可能重新启动。关机恢复不等于进程重新创建。测试首次进入、重复执行、直接重入、切换其他程序后进入、取消与文件缺失；对每种状态明确资源归属。

## 动态代码和分页

### 写完代码不等于 CPU 将执行新内容

代码缓存需要在所有写入和重定位完成后同步，再注册异常信息、发布入口并执行。数据缓存和指令缓存可能分离。仿真器缺少真实缓存行为时，成功运行不能排除陈旧代码。

### 活动代码不能随意换出

函数返回地址、异常帧、回调指针和对象内部指针可能仍指向模块。卸载规则应考虑所有这些引用；模块函数已经返回，不代表所有引用都结束。导入身份必须对应当前主程序，不能跨不同 ELF 复用地址表。

### 文件读取接口不等于文件执行映射

文件可能由多个 Flash 碎片组成。取得第一片地址不代表连续映像，打开文件也不代表物理块固定。跨设备复制私有系统调用编号、页面大小或 OS 地址，会把一个型号的经验变成另一个型号的故障。

### 分页有常驻成本与访问模式条件

代码分页帮助减少主文件体积，但加载窗口会占 RAM；把原本 Flash 直接执行的代码搬入 RAM，不会自动释放计算堆。数据换出只有在存在较多暂不用对象时才可能有效。频繁访问超过窗口的对象会导致反复读写，且分页管理器自己不能在缺页处理时再次缺页。

对含指针对象做数据换出，要么保持虚拟地址，要么保存并恢复对象引用关系。不能把原始堆字节写入文件、释放后换地址读回就继续使用旧指针。

## 测试和性能证据

### 正反例与失败后的可用性

门禁既要拒绝坏输入，也要接受已知好输入；否则“全部拒绝”也可能看似安全。对 OOM、损坏 LIB 和语法错误，检查拒绝位置、清理、旧状态和下一次正常操作。对照实现保留原错误结果，不能因为新实现产生另一种错误就算一致。

### 测试驱动不要降低难度冒充通过

不要为适应主机插桩而偷偷扩大设备预算，不要提前预热失败场景中的缓存，不要删掉刚发现的失败输入，不要把超时/OOM 算成数学正确。允许专用主机预算，但报告应明确它与目标配置不同。

### 保持输入和版本一致

输入、生成源码、编译命令、目标库、链接脚本、实际 ELF、运行器、结果都要能关联。文件名叫 `bridge24.o` 不证明里面是 24 KiB。源目录改动后，旧对象和新源码必须分开标识。

### 栈报告与实际峰值不同

编译器单函数 `.su` 不包含完整递归链、中断、驱动和 OS 切换。主机与目标帧布局不同，插桩进一步扩大差异。静态栈分析、目标执行与设备边界测试应各自说明范围。

### 速度比较需要同工作负载

先校验输出等价，再做轮换顺序、冷/热分开、重复次数和离散程度统计。QEMU 主机墙钟不等于设备时间；指令轨迹也不直接等于周期。构建时间、计算时间、文件换入时间和 UI 响应时间应分别比较。

## 环境与协作管理

### 单独恢复任务环境

用户 WSL 或 VM 故障时，先诊断进程和存储，保留镜像、密钥与配置。不要用全局服务重启或重装掩盖问题。可用专属隔离环境恢复工作，但必须说明哪些源是权威、哪些是副本，以及下一次如何同步。

### 并行工作需要文件所有权

为代理/同事分配明确的文件范围和产物，不让两人同时修改同一生成器。源文件合并后必须做组合验证；两项独立修复各自通过，不代表合并后顺序、析构与回滚仍正确。

对子任务报告要求实际命令、退出码、产物哈希、失败副本和范围。主任务抽查关键主张，尤其是所谓“实机已过”“完全一致”“全部功能保留”。转述不是独立验证。

### 长期工作以状态文件交接

聊天历史会截断，人工记忆也会混淆旧数字。维护最新状态、历史变更、阻塞与未知、产物位置和下一步前置条件。暂停时明确保留哪些工作，恢复必须重新确认关键身份，而不是从最新一条自然语言猜测整个环境。

## 文档和发布

### 更正结论而不改写历史

旧预算、失败日志、被否定的方案应保留。新增明确的更正说明及索引，让读者知道哪个结论适用于当前版本。把旧报告全部改成新数字会破坏当时输入、哈希与决策的可追溯性。

### 让命令可审查

每条操作写前置环境、工作目录、输入、输出、会修改什么、怎样判断成功。模板参数用清楚的占位符，不把过期绝对路径包装成可直接运行。清理命令写出可恢复来源；不要把初始化、下载、构建、打包和发布藏在一个模糊脚本名后面。

### 把发布包与研究包分开

容量测量 ELF、扩大链接地址的候选、无 CAS 的诊断、宿主程序，都不应与可安装产品同名交付。发布需有明确 manifest、长度、哈希、目标设备、功能范围与已验证状态。研究包应能追查失败，但不能被误认为“最新可用版”。

## 可直接复用的检查顺序

1. 固定用户需求、设备/系统、允许删改范围和验收动作。
2. 保存已工作产物与源码依赖身份，建立可重建基线或明确复现缺口。
3. 量总存储、单文件、ROM、静态 RAM、堆和栈，明确每个限制来源。
4. 单变量改变架构或记录必须同时改变的因素。
5. 对正确输出、资源失败、取消、恢复和生命周期分别验证。
6. 计算完整产品净成本，包含加载器、元数据、缓冲与外部文件。
7. 将主机、目标仿真、静态分析与实机证据分别记录。
8. 固定源与产物哈希，做组合验证，再决定合并或发布。
9. 对收益不足的路线按预设条件停止，保留证据，不将目标改写成已完成。
10. 暂停时保存状态和恢复手册，避免下一位开发者重新踩同样的坑。
